# Admin cascade audit, round 2 (R2-ADMIN)

Owner ask: "don't forget the cascade effects on the admin side, fix them if you can". Every setting, state, content
type or metric shipped in round 2 (R2-00 to R2-19, the game-over card, release 1.37.1) was checked end to end in the
admin console: runtime settings with range checks and helper text, content tools, dashboards with CSV export,
moderation, audit log entries and roles.

Status: **exists** (was already complete), **fixed** (a gap closed in this pass), **partial** (works, with a noted
limit), **not done** (with the reason; also in `docs/qa/FOLLOW_UPS.md`, Round 2).

All migrations below are new in this pass and must be applied in order before the deploy (the lead applies them):
`20261202000101` to `20261202000701`. Until they are applied, the Library copy overrides and the `warm` split fall
back quietly, and the new Metrics cards read "n/a".

## Settings

Every setting is defined once in `lib/game-settings/schema.ts` (kind, range or options, default, helper text). The
admin Settings page (`components/admin/SettingsPage.tsx`) renders every entry from that schema, grouped, with its
help, default and range; `PUT /api/admin/settings` validates against the same schema (`validateSetting`), writes
`audit(ctx, "setting.update", "setting:<key>", {before, after})`, and needs `settings.write` (owner).

## Roles

Every route under `app/api/admin` is in the role matrix of `tests/api/admin.test.ts` (the "covers every route file"
test). The one new route, `GET /api/admin/games/practice`, uses the existing `content.read` permission
(`lib/admin/roles.ts`: owner and content editor) and is in the matrix. Pages hide what a role cannot do; the server
refuses it (`requireAdmin`).
